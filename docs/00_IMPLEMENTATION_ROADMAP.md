# Phase 00 — Implementation Roadmap

2026-09-17. Repository-aware baseline: the workspace was empty and not a Git repository. There is no production system to migrate or refactor. All outputs below other than Phase 00 documents are future work. Do not begin Phase 01 without the next user instruction.

## Dependency and release rules

Preserve all 30 phases, their names and separate theme specifications. Each row is a bounded phase contract, not evidence of implementation. Phase dependencies refer to foundations/contracts unless a production dependency is explicitly stated. UI work in 05–17 can use clearly isolated development fixtures, never fake production endpoints. It is not publicly releasable until real project/media/watermark/SEO integrations in 18–20 pass. Define their contracts in 01/02 rather than pulling future features into Phase 00.

Security architecture starts in 03 and applies to each phase, not only final hardening. SEO contracts start in 01/02 and constrain public rendering before Phase 20 completes integrations. Teams/client approvals/custom domains have early schema preparation but later release gates. Matrix priorities distinguish V1, V1.5, V2 and Future, regardless of phase number. Phase 27 is mostly V1.5; its V1 ownership/reporting controls are implemented at first public publication and audited there. Phase 28 V1 entitlements/usage foundation does not imply V2 client invoices/payments.

Every implementation phase follows master §32: inspect prior state/docs, assess dependencies/migrations/security/SEO/mobile, then build/test/lint, inspect warnings and validate loading/empty/error, authorization, mobile/desktop, accessibility/performance and applicable SEO. Record actual results and known limits. The phase-specific tests below supplement these common checks.
